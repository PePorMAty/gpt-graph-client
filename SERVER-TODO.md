# Что осталось сделать на сервере

Живой список серверных задач, которые нужны фронту после редизайна. Собран по
тому, что уже реализовано в клиенте и упирается в бэкенд.

Обозначения:

- **Есть** — эндпоинт работает, менять не надо.
- **Сделано** — закрыто, обе стороны на месте.
- **Нужно** — клиент уже умеет это вызывать, сервер ещё нет.
- **Позже** — договорились отложить, но заложено в интерфейсе.

Базовый префикс — `VITE_API_URL`.

---

## 1. Библиотека графов

### Что уже есть

| Метод                       | Назначение                          |
| --------------------------- | ----------------------------------- |
| `GET /graph-files`          | список сохранённых графов           |
| `GET /graph-files/{id}`     | файл графа целиком                  |
| `POST /graph-files/save`    | сохранить новый граф                |
| `PUT /graph-files/{id}`     | перезаписать существующий           |
| `PATCH /graph-files/{id}`   | переименовать (`{ name }`)          |
| `DELETE /graph-files/{id}`  | удалить                             |

### Сделано

**1.1. Описание графа («О графе»).** Поле `description` есть в модели графа,
принимается в `POST /graph-files/save`, `PUT` и `PATCH`, отдаётся и в списке, и
в `meta` файла. `PATCH` правит `name` и `description` по отдельности — раньше он
требовал `name` и отвечал 400 на запрос с одним описанием.

**1.2. `updatedAt` у всех графов.** Проставляется при любом изменении, включая
создание. У графов, сохранённых до этой правки, поле пустое — там по-прежнему
показывается дата создания.

**1.3. Лёгкий список.** `GET /graph-files` отдаёт только мету (`id`, `name`,
`createdAt`, `updatedAt`, `leafCount`, `description`) без узлов. Заодно список
перестал падать целиком из-за одного постороннего или битого файла в каталоге:
такие пропускаются с записью в лог.

Попутно в `PUT` починена потеря `description` и `sources`, когда клиент их не
прислал: обычное «Сохранить» шлёт только узлы, и прежняя версия стирала оба
поля.

### Позже

**1.4. Превью графа.** Сейчас клиент рисует превью сам по узлам из файла — для
этого приходится грузить весь граф при выборе в списке. Если в списке будут
сотни графов, имеет смысл отдавать в мете компактный слепок (например
`preview: { nodes: [{x, y, w, h, type}] }`) или заранее сгенерированный SVG.

**1.5. Постраничность и поиск.** Пока весь список фильтруется на клиенте.
При росте числа графов понадобятся `?query=&limit=&offset=&sort=`.

## 2. Закладки — **сделано**

Закладки сохранённого графа лежат на сервере отдельным ресурсом (сайдкар рядом
с файлом графа, а не внутри него): закладку ставят на лету, и она переживает
перезагрузку вкладки, даже если сам граф ещё не сохраняли.

**2.1. Модель.** Закладка = `{ graphId, nodeId, label, kind, note, createdAt }`,
где `kind` — `product | transformation`. Ключ — пара `(graphId, nodeId)`.

**2.2. Эндпоинты.**

| Метод                                          | Назначение                       |
| ---------------------------------------------- | -------------------------------- |
| `GET /graph-files/{id}/bookmarks`               | закладки графа                   |
| `PUT /graph-files/{id}/bookmarks/{nodeId}`      | создать/обновить (`label`,`note`)|
| `DELETE /graph-files/{id}/bookmarks/{nodeId}`   | удалить                          |

Клиент (`graphExtrasMiddleware`) шлёт каждую правку сразу, локальное состояние
остаётся ведущим — интерфейс не ждёт ответа. Пока полотно не сохранено, закладки
копятся в памяти и уезжают на сервер при первом сохранении.

**2.3. Переживание правок графа.** Удалённый узел уносит свою закладку и на
сервере, удалённый граф — весь свой набор.

Осталось: при **объединении графов** узлы получают новые id, и закладки на них
не перепривязываются — просто теряются. Если объединение станет частым
сценарием, понадобится карта «старый id → новый» на стороне клиента.

## 3. История действий — **сделано**

`historyMiddleware` по-прежнему записывает действия над графом, а
`graphExtrasMiddleware` отправляет их на сервер, если граф сохранён.

**3.1. Модель.** Запись = `{ id, graphId, at, kind, title, details, nodeIds }`.

| Метод                                 | Назначение                      |
| ------------------------------------- | ------------------------------- |
| `GET /graph-files/{id}/history?limit=` | последние записи графа         |
| `POST /graph-files/{id}/history`       | добавить запись (батчем)        |
| `DELETE /graph-files/{id}/history`     | очистить                        |

**3.2. Отправка пачкой.** Записи копятся полторы секунды и уходят одним
запросом. Когда вкладку закрывают, остаток досылается через `sendBeacon` —
иначе браузер оборвал бы обычный запрос.

**3.3. Что на сервер не уходит.** «Граф открыт» и «Полотно очищено» описывают
сессию на полотне, а не правку файла, — от них серверный список только распухал
бы при каждом открытии. Такие записи остаются в памяти вкладки.

**3.4. Очистка.** Кнопка «Очистить историю» чистит и на сервере. Смена графа —
нет: она обнуляет только локальный список.

Лимит записей — 300, одинаковый на клиенте и на сервере, иначе список после
перезагрузки оказался бы другой длины.

---

## 4. Уведомления

В шапке есть колокольчик с историей уведомлений о запросах к модели. Список
собирается на клиенте из событий текущей сессии. Серверная часть нужна, только
если уведомления должны переживать перезагрузку или приходить из фоновых задач
(например, долгое построение цепочки) — тогда понадобится
`GET /notifications` и, в идеале, SSE/WebSocket.

## 5. Промышленные данные (ГИСП)

В интерфейсе это есть в трёх местах, и везде пока заглушка:

- переключатель «Промышленные данные» в панели над холстом;
- вкладка «Промышленные данные» в карточке продукта;
- вкладка «Промышленные данные» в библиотеке;
- счётчик «Подтверждено в ГИСП» в строке состояния.

**5.1. Что нужно от сервера.** Поиск продукта графа в реестре ГИСП и выдача
по нему карточки:

```
POST /industry/lookup
{ "products": ["Полипропилен", "Этилен"] }

→ {
  "Полипропилен": {
    "found": true,
    "producers": [
      { "name": "…", "inn": "…", "region": "…", "registryStatus": "…", "url": "…" }
    ]
  },
  "Этилен": { "found": false }
}
```

**5.2. Чего хватит для первого шага.** Достаточно флага «есть в реестре» по
названию продукта — счётчик в строке состояния и бейджи на узлах уже
рассчитаны на него. Полные карточки производителей можно добавить вторым
этапом.

## 6. Объединение графов

Объединение целиком считается на клиенте (`useMergeGraph`): совпадающие
продукты схлопываются, источники и цвета презентаций сливаются, раскладка
пересчитывается через ELK. Сервер в этом не участвует и, скорее всего, не
должен.

Единственное, что может понадобиться: **сохранение результата как нового
графа** — сейчас результат остаётся на полотне и сохраняется обычным
«Сохранить». Если захочется «Объединить и сохранить как…», хватит
существующего `POST /graph-files/save`.

## 7. Мелочи

- **`GET/PUT /graphs/prompt-layout`** — шаблон промта, **сделано**. Раздел
  «Создание графа» запрашивает шаблон при каждом открытии панели, а кнопка
  «Сохранить шаблон» под полем отправляет правку в `PUT`. Правленый шаблон лежит
  в файле; переменная окружения `GPT_PROMT_LAYOUT` осталась дефолтом на случай,
  когда файла нет. «Сбросить шаблон» очищает только поле — чтобы сброс запомнился,
  его надо сохранить.
- **Шаринг (`/graphs/share`)** — работает, отдельных задач нет.
- **Экспорт** — целиком на клиенте (JSON), сервер не нужен.
